# Рефакторинг (SRP)

## Когда применять
- Тесты зелёные, ревью блокеров нет или они закрыты.
- Шаг 8 пайплайна: чистка без смены API и JSON.
- Типичные запахи: mapper-бин, сервис в mapper, толстый контроллер, сервис с чужим репозиторием.

Не применять, если тесты красные, нет покрытия поведения или просят новую фичу.

## Что делает (процедура)
1. Зафиксировать контракт: эндпоинты, статусы, поля response, тексты исключений. Тесты не менять (не ослаблять, не переписывать под рефакторинг).
2. Один запах — один шаг. После шага: `./gradlew test`. Откатить шаг, если покраснело.
3. Делать только то, что уже нарушает rules на **этом** диффе, не «улучшить весь пакет».

## Разрешённые ходы
- Mapper `@Component` → `public final` + private ctor + static `toX` / `toResponse`, как `TagModelMapper`.
- Убрать сервис из mapper: средний рейтинг / count считать в сервисе своей сущности или в контроллере после `service.get*`, не в `toResponse`.
- Контроллер: оставить `request → mapper → service → mapper → response`. Логику из контроллера вернуть в сервис.
- Сервис: чужие сущности только через их `*Service`; инварианты — private `ensure*` в том же классе.
- Репозиторий: удалить неиспользуемые методы; у `Page` + fetch добавить `countQuery`.
- Имена полей: в сервисе `repository`, в контроллере `service`. Конструктор без `@Autowired`.

## Запрещено
- Менять URL, HTTP-статусы, JSON-поля, тексты ошибок.
- Добавлять поведение (новый фильтр, JWT вместо `userId` в теле) — это отдельная задача.
- Новые слои, абстракции «на будущее», общие `*Utils`.
- Переписывать тесты, чтобы они проходили после рефакторинга.
- Рефакторить соседние сущности вне диффа.

## Пример
**Вход:** зелёный Review, `ReviewModelMapper` — бин, `RestaurantModelMapper` зовёт `ReviewService`.
**Выход:** static `ReviewModelMapper`; `averageRating` / `reviewsCount` собираются вне mapper. Тесты те же и зелёные.
